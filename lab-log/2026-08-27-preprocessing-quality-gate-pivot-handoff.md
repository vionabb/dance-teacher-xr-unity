### Working in a worktree against this data: a gotcha

`data/reference_motions/{videos,pose-raw}` and `data/participant_motions` are gitignored (patterns end in `/`, i.e. "match a real directory"), but a git worktree doesn't share the primary checkout's untracked local data cache. If you're in a worktree and need the real corpus, symlink the specific gitignored subdirectories back to the primary checkout rather than re-staging ~4.5GB via rclone. **Git's ignore matching does not treat a symlink-to-a-directory as a directory**, so these symlinks show up as untracked, not ignored — `git add -A` or `git add .` will happily stage them (an absolute, machine-local path that would break on any other machine or checkout). Always stage specific filenames explicitly in a worktree with this setup; never use a broad add.

## Out-of-frame and hallucination analysis (2026-08-30, full 1,808-clip corpus)

Prompted by Viona: before excluding "poorly framed" videos as a quality gate, quantify how much of the corpus that would actually throw away, and how often MediaPipe reports high confidence for a landmark that's genuinely out of frame.

**Method**: for each of the 8 upper-body landmarks CHI25's automatic rating used (`LEFT`/`RIGHT_SHOULDER`, `_ELBOW`, `_WRIST`, `_HIP`), compare each frame's raw pixel-space `_x`/`_y` against the actual video's width/height (via `cv2.VideoCapture` metadata). A landmark is unambiguously out of frame when its coordinate falls outside `[0, width) x [0, height)` — MediaPipe only reports a coordinate there when it's extrapolating past the visible image, so this is exact ground truth, not a heuristic. Full corpus, all 1,808 clips, ~13ms/clip.

**How much would exclusion throw away**: 59.3% of clips have *some* frame with an out-of-frame CHI25 landmark; even a lenient ">20% of frames" threshold excludes 38.3%. **Simple exclusion isn't viable.**

**It's a hip problem, not an arm problem**: per-landmark out-of-frame rate across all frames — `LEFT_HIP` 18.2%, `RIGHT_HIP` 17.7%, `LEFT_WRIST` 10.1%, `RIGHT_WRIST` 8.7%, `LEFT_ELBOW` 1.6%, `RIGHT_ELBOW` 1.6%, `LEFT_SHOULDER` 0.3%, `RIGHT_SHOULDER` 0.1%. Hips leaving frame is normal, expected waist-up webcam framing in this corpus, not a quality defect in itself — and it's an issue CHI25's own 8-point scheme inherited too, since it includes hips.

**Restricting to the 6 arm/shoulder landmarks** (the ones that actually matter for TikTok-style arm choreography): still 54.9% of clips have *some* out-of-frame arm landmark; a >20%-of-frames threshold excludes 29.6%, and it's heavily corpus-dependent — reference dance tutorials are essentially unaffected (0% excluded at that threshold; they're framed full-body by design), `chi25_study1` loses 16.7%, `chi25_study2` loses 39.1% (self-recorded webcam framing is tighter/less consistent).

**Hallucination rate** (MediaPipe reporting `_vis > 0.5` for a landmark that is genuinely out of frame): overall 35.6% across all 8 landmarks, but it varies a lot by landmark — `LEFT_WRIST` 8.7%, `RIGHT_WRIST` 5.5% (fairly trustworthy: when a wrist leaves frame, `_vis` usually does drop, so a wrist-visibility gate is reasonably safe to build on), `LEFT_HIP` 50.0%, `RIGHT_HIP` 52.2% (a near coin flip — don't trust hip `_vis` as an out-of-frame signal), `LEFT_ELBOW` 29.2%, `RIGHT_ELBOW` 14.2%, `LEFT_SHOULDER` 94.8%, `RIGHT_SHOULDER` 97.9% (shoulders rarely leave frame, but when they do, MediaPipe is confidently wrong almost every time — low frequency but worth a hard caveat if shoulder visibility is ever used as a gate).

**Scripts**: written to the session scratchpad, not yet promoted into the repo (`analyze_out_of_frame.py` — per-clip, all 8 landmarks; `arm_only_oob.py` — 6-landmark variant with the clip-level exclusion-threshold table; `per_landmark_oob.py` — the per-landmark breakdown above). Worth moving into `motion_extraction/scripts/` if this analysis needs to be re-run or extended rather than re-derived from this summary — they iterate `data/reference_motions` and `data/participant_motions` directly via `cv2`/`pandas`, no dependency on the quality-triage batch, and each takes well under a minute for the full corpus.

## Occlusion-error detectability (2026-08-30)

The out-of-frame work above has a clean automatic signal (pixel coordinates vs. frame bounds). Occlusion — a limb passing behind or in front of another body part while still on-screen — doesn't have an equally obvious one, and Viona pushed back on assuming it's undetectable from pose data without actually testing it first.

**Test**: built a geometric proxy (does `RIGHT_WRIST_x` cross to the opposite side of the shoulder midline, i.e. `(LEFT_SHOULDER_x + RIGHT_SHOULDER_x) / 2`) and checked whether frames matching it have a higher `select_suspicious_frames.py` suspicion score, against `quality-triage-033`, where Viona's own note says "shoulder tracking is good, but arm tracking deteriorates when right arm crosses body."

**Result**: negative/inconclusive. In that clip, 37/44 frames matched the crossing heuristic (it's true almost all the time, including frames Viona didn't flag), and mean suspicion score was actually *lower* on crossing frames (0.545) than non-crossing frames (0.827) — the opposite of the expected direction, though driven by a small non-crossing sample. The crude midline-crossing definition doesn't discriminate.

**Interpretation, not yet confirmed**: this is one clip and one naive proxy, not a disproof that occlusion is undetectable — but it's consistent with the mechanistic story in Status above: occlusion tends to produce a smooth, confident wrong guess rather than a velocity spike or visibility dip, which is exactly what `select_suspicious_frames.py`'s scoring formula keys off. A better proxy would need a different signal entirely (candidates not yet tried: 3D depth ordering if `pose3d` distinguishes which landmark is nearer the camera; a multi-frame trajectory-plausibility check spanning the whole occlusion event rather than per-frame velocity; or simply accepting this needs Viona's own labels via `error_marking` rather than a from-scratch heuristic).

**Decision**: don't invest further in a from-scratch geometric occlusion detector without real per-frame ground truth to validate against — that's exactly what `error_marking` (below) is for.

## New annotation-tool task types: `error_marking` and `video_quality_rating` (2026-08-30)

Built directly off the findings above: out-of-frame errors have a good automatic signal now, but occlusion errors and the general "how often is X wrong" question need Viona's own labels, and lighting/clothing quality needs a lightweight per-video (not per-clip) rating pass.

### `error_marking`

Lets an annotator mark frame-range occurrences of a body part's inaccuracy on a clip, with one or more probable causes attributed to each mark. **Schema as of 2026-09-02** (superseding the original single-`error_type` design described below — see "Error-marking timeline redesign" for the full UI rebuild that went with this): `error_marking_response_json` = `{"marks": [{"body_part": str, "start_frame": int, "end_frame": int, "causes": [str], "note": str}], "no_errors_found": bool, "note": str}` (`server.py`'s `_validate_error_marking_response`; per-mark `note` capped at `ERROR_MARK_NOTE_MAX_LENGTH` = 500 chars, `body_part`/each `cause` at `ERROR_MARK_LABEL_MAX_LENGTH` = 64). `status: "completed"` requires either at least one mark or `no_errors_found` set (so "reviewed, found nothing" is distinguishable from "not yet reviewed") — the UI no longer has a checkbox for this; it confirms in a dialog at complete-time instead (see redesign section). Both `body_part` and each `cause` are **deliberately not closed enums server-side** (any non-empty string ≤64 chars) — per Viona's explicit request, editable vocabularies (add/rename/remove), persisted in the browser's `localStorage`, not the server, so it's per-device. Seeded defaults live in both `server.py`'s `DEFAULT_ERROR_BODY_PARTS`/`DEFAULT_ERROR_CAUSES` (served via `/api/state`) and `app.js`'s `FALLBACK_ERROR_LISTS` (used before that response lands); keep the two in sync by hand if you change either.

Frame indices are local to the displayed `clip.mp4` (frame 0 = the first frame of that rendered window), not positions in the original source video — this may matter for any reference-corpus clip in this pilot batch that was rendered from a windowed span of a longer source video rather than a short clip in its own right; not yet flagged to Viona or resolved, worth checking if her review of those tasks surfaces confusion about what a frame number refers to.

Generator: `append_error_marking_tasks.py` — reuses the already-overlay-burned `clip.mp4` artifacts from an existing `quality_triage` batch (no new rendering), targeting whichever `quality_triage` task_ids you pass it. **Pilot batch**: the 17 clip-based tasks Viona already marked "problematic" in her 34 (`error-marking-000`...`016`) — a deliberately high-value first set, since they're clips already known to contain a real error.

### `video_quality_rating`

Rates one video's **lighting** (good / moderate / poor — contrast/exposure) and **clothing suitability** (well-suited / moderate / poorly-suited — form-fitting-or-bare-arms vs. baggy) from one representative (un-overlaid — this rates the source recording, not the tracking) frame at the midpoint of the video. Schema: `quality_rating_response_json` = `{"lighting": str, "clothing": str, "note": str}`, both required on `completed`. Generator: `append_video_quality_rating_tasks.py` — samples one frame per **unique video**, where for participant corpora "video" means one recording session (everything before `____clipN` in the filename), not one segmented clip, since lighting/clothing don't change mid-session. **Pilot batch**: 20 videos, fixed seed 20260830 (6 reference + 7 `chi25_study1` + 7 `chi25_study2`), `video-quality-000`...`019`. Claude's own ratings for all 20 are already recorded under annotator `claude` in the same database — compare against Viona's once she's rated the same 20, per "Next actions" above.

### Two real UI bugs found and fixed while building this

1. **The whole tool was rendering unstyled** (plain-text buttons, borderless inputs) — not specific to the new screens. Root cause: `index.html` loaded daisyUI 5 (a Tailwind v4 plugin) alongside the deprecated Tailwind v3 Play CDN (`cdn.tailwindcss.com`); that combination silently no-ops every daisyUI class. Fixed by switching to the Tailwind v4 browser CDN (`https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4`). This fixed rendering across every screen, not just the new ones — if the tool looks "rough" again in a future session, check this CDN pairing first before assuming a CSS/markup regression.
2. **`error_marking`'s "Mark end here" button wasn't actually disabled** despite the markup/JS setting `disabled` correctly on render — `lockInteraction(false)` (called after every task navigation) force-re-enables every button/input/select/textarea in the workspace indiscriminately, clobbering any screen's deliberately-conditional disabled state. Fixed by having `lockInteraction` re-apply the error-marking screen's disabled state right after unlocking. Worth remembering if a future screen ever needs a conditionally-disabled control: this same clobbering will happen again unless it's added to `lockInteraction`'s post-unlock re-sync too.

Both fixed and committed as of `56ace6f`.

## Corpus-wide frame-quality map (2026-08-31)

Per Viona's request: a reusable, re-runnable visualization of the whole participant corpus (not just a pilot batch), meant to inform which clips to exclude for metric evaluation and to guide a future frontend camera-setup guidance screen.

`motion_extraction/scripts/render_corpus_frame_quality_map.py` renders one pixel-row per participant clip (study1 + study2, 1,756 clips -- reference excluded), one column per frame (resampled to 200 columns with worst-severity pooling, so a bad frame in a long clip doesn't get averaged away), colored by the same arm/shoulder-landmark logic as the out-of-frame analysis above: **white** = no detected issue, **yellow** = correctable (an arm/shoulder landmark out of frame but with correctly-low reported visibility, or a moderate suspicion-score spike -- interpolatable), **red** = uncorrectable (an out-of-frame landmark with a confidently-wrong *high* visibility report -- a hallucination -- or a severe suspicion spike). The suspicion-score yellow/red cutoffs are the corpus-wide 75th/95th percentiles, computed in a first pass over the actual data rather than guessed. Rows are grouped by which reference dance the clip performs (parsed from the participant filename, normalized past the two studies' inconsistent naming -- "mad-at-disney" vs "madatdisney") and ordered worst-to-best by a badness score within each group.

First full run (`temp/experiments/20260831-033057-frame-quality-map/`, not committed -- `temp/` is gitignored, re-run to reproduce): **frame-weighted 63.9% white / 28.5% yellow / 7.6% red**; **17 of 1,756 clips are more than half red** -- a concrete, ranked starting point for exclusion decisions (see that run's `frame_quality_summary.csv`, sorted worst-to-best within each dance group, for the full list rather than reading pixels off the PNG).

Re-run anytime with `uv run python -m motion_extraction.scripts.render_corpus_frame_quality_map` (takes ~45 seconds for the full corpus; `--max-clips N` for a fast dry run, `--output-root` to control where it's written -- defaults to a fresh timestamped `temp/experiments/` directory so successive runs stay comparable as the preprocessing methodology changes). Row unit is the **clip**, not the recording session -- if Viona wants session-level rows instead (one row per participant's whole recording rather than per segmented move), that's a different aggregation this script doesn't currently do.

## Error-marking timeline redesign (2026-09-01/02)

Driven entirely by a sequence of Viona's own short, iterative UI requests against the live server (she was actively annotating `error-marking-009` through several of these pushes — see "Blocked right now" above), not by a new finding. The `#error-marking-screen` went from the original body-part-select-plus-Mark-start/end-buttons design to a fully timeline-driven one, across five commits on this branch: `909ab96` → `085ead6` → `9804023` → `faf1e20` → `07009a5`.

**Current interaction model**, in the order it was built up:

1. **One labeled timeline row per body part** (`909ab96`, extended `085ead6`), grouping every mark for that body part onto the same row instead of one row per mark. Every body part in the vocabulary gets a row up front, whether or not it has marks yet (`085ead6`) — `timelineRowGroups()` in `app.js`.
2. **Three ways to create a mark**, all converging on the same popup: click-drag an empty part of a row (`085ead6`); click a labeled per-row **+** button to drop a mark at the current playhead frame, disabled when that frame is already covered by an existing mark on that row (`9804023`, `addMarkAtCurrentFrame`/`frameCoveredForPart`); or drag either edge of an existing mark to resize it, live-seeking the video to match the dragged frame (`085ead6`/`909ab96`, `startTimelineHandleDrag`/`startNewMarkDrag`). The old body-part-select + "Mark start here"/"Mark end here" fieldset above the timeline is gone (`9804023`) — the per-row **+** button plus click-drag fully replace it.
3. **Clicking an existing mark opens a popup** (`error-mark-dialog`) with a canvas preview frame captured from the mark's midpoint, the cause chips (multi-select, editable vocabulary via "Edit cause list" inside the popup itself), a per-mark note field (`9804023`), and Remove. **A plain tap on an edge handle, with no drag, also opens the popup** (`9804023`) — on a very short mark the handles can cover its whole visible width, so a tap on the segment body alone wasn't always reachable; confirmed this actually reproduced before adding the fix.
4. **Segments are colored by their assigned cause(s)** — a fixed palette keyed to each cause's position in the vocabulary, gray for "no cause set," a diagonal stripe blending each cause's color when a mark has more than one — with a legend under the rows (`085ead6`).
5. **Long clips scale via horizontal scroll, not by squeezing every frame smaller** (`9804023`): the timeline enforces a minimum of `MIN_TIMELINE_PX_PER_FRAME` = 6px/frame; once that would need more width than the row has, only the track area scrolls (`.timeline-scroll`), while the label/+-button column (`.timeline-left-col`) stays fixed and always reachable. Verified at a narrow viewport that this actually engages and that the label column doesn't scroll away with it.
6. **Completing with zero marks now confirms in the moment** instead of requiring a checkbox first (`9804023`): the old "No errors observed in this clip" checkbox is gone; clicking Complete with an empty mark list opens a native `confirm()` asking to complete as "no errors observed," and only submits `no_errors_found: true` on explicit confirmation — verified both the accept and cancel paths actually take effect (cancel correctly leaves the task un-submitted and the queue position unchanged).
7. **Body-part list editing moved inline** (`faf1e20`, relabeled `07009a5`): the old "Edit body-part list" button (which opened the shared list-manager modal) is gone, replaced by a small "Edit" toggle below the bottommost row in the timeline's label column. In edit mode, each row's **+** is replaced by a red ⊖ delete button, and a **+** row appears at the bottom for adding one — click it and it becomes an auto-focused text input; Enter or losing focus commits the typed label, or cancels silently if left blank. **Found and fixed a real double-submit bug here**: committing via Enter re-renders and removes the input as part of committing, which synchronously fires a cascading `focusout` on the now-detached element with the same value still in it — `commitNewBodyPart()` checks `state.addingBodyPartEntry` (already cleared by the first call) before doing anything, so the cascading second call is a no-op. Confirmed this actually double-submitted before the guard was added, and that it doesn't after.

**Data-model side effects, both migration-safe:**
- **Merged "Right hip"/"Left hip" into one "Hips" body part, and renamed "Torso" to "Shoulders"** (`9804023`), per Viona's request. Both server (`DEFAULT_ERROR_BODY_PARTS`) and client (`FALLBACK_ERROR_LISTS`) defaults updated; `torso` keeps its id (only the label changed) so historical marks tagged with it keep displaying correctly under the new label with no migration needed. The hip merge does change id (`right_hip`/`left_hip` → `hips`), so `app.js`'s `migrateBodyPartDefaults()` runs once per page load against a device's already-persisted `localStorage` list: it folds a still-default "Right hip"/"Left hip" pair into "Hips" and re-labels a still-default "Torso" to "Shoulders", but only touches entries that still match the shipped defaults exactly — a customized list, or a list that already has both changes applied, is left alone. **This was watched migrate live** on the `claude-ui-check` test browser, which still had the pre-merge list persisted. Any already-submitted judgment referencing the old `right_hip`/`left_hip` ids is untouched (append-only, as designed) and still renders correctly via the existing "stray id" fallback in `timelineRowGroups()` — it just shows as its own small row using the raw id as a label rather than folding into "Hips".
- **Each mark now carries an optional `note`** (see the corrected schema in "New annotation-tool task types" above). Existing marks (including Viona's own in-progress `error-marking-009`) get `note: ""` backfilled on load via `{causes: [], note: "", ...mark}` in `renderErrorMarkingTask` — no data loss, nothing required from her.

## Context (why this work exists)

The 2026-08-27 pivot paused smoothing-parameter work because source-video quality issues (framing/crop, lighting, backdrop) and pose-detection quality issues (jitter, gaps, hallucinated/false limb tracking) dominate the corpus and confound any smoothing comparison. That entry's proposed next step was to validate automatic quality detectors against the ~30 existing human `usable`/`constrained`/`weak` labels — but Viona decided those labels are insufficient (a byproduct of other targeted sessions, not a systematic pass) to validate a detector's precision/recall. This plan extends the annotation tool with a purpose-built workflow to gather that ground truth efficiently across the full local corpus: **1,808 per-clip videos** (52 reference + 675 study1 + 1,081 study2 — see "Corpus-size correction" above for why this isn't 1,955), already staged locally via rclone (confirmed on disk 2026-08-28).

## Decisions already made (do not re-litigate without asking Viona)

- **Sampling**: automatic-flagged candidates **plus** random unflagged controls, so resulting labels can validate both precision and recall of any detector.
- **Overlay always on**: every review item shows the skeleton overlay burned in, never raw video/frame alone. Viona's own reasoning: pose estimation can perform fine on a poor-looking video, or poorly on a good-looking one — video quality and pose quality are independent judgments and both need to be visible together.
- **Two-stage workflow**: a fast Stage 1 pass classifies each item fine vs. problematic (no factor detail — kept fast on purpose); only problematic items get an auto-generated Stage 2 follow-up task where Viona localizes the specific bad span and its cause, **warm-started** with a guessed span/cause from the automatic signals that she adjusts rather than marking from scratch.
- **Review-unit routing**: statically-flagged candidates (crop, lighting) shown as a single frame; temporally-flagged candidates (roughness, false-tracking) and random controls shown as a short clip. Both always carry the burned-in overlay.
- Cropping is detected automatically from hip/shoulder landmark position relative to frame bounds (Viona's own suggestion).
- New `SOURCE_EVIDENCE_FACTORS` tags `false_tracking` and `track_discontinuity` will be added — both named explicitly in the 2026-08-27 lab log's "Proposed path forward" but not covered by the current tag set (`motion_blur` conflates video-side blur with detector-side hallucination).
- `_load_corpus_membership` (in `run_preprocessing_experiment.py`) is **not reusable** for corpus-wide enumeration — it hard-asserts exactly 25 rows and is scoped to one staged experiment. Use `dance_teacher_pose.schema.collect_pose_data_files` directly against each corpus's raw-pose root instead (confirmed paths below).
- No blur/optical-flow/false-tracking detector exists anywhere in the repo today — this is genuinely new code, not a refactor of something existing. The only prior art is a single-frame luminance/contrast snippet in `append_targeted_preprocessing_tasks.py` (~line 83-97).
- **CHI25's own 8 upper-body landmarks** (`LEFT`/`RIGHT_SHOULDER`, `_ELBOW`, `_WRIST`, `_HIP`) are the reference landmark set for any future framing/out-of-frame analysis, matching what the thesis's automatic rating actually used — not all 33 MediaPipe pose landmarks.
- **Hip out-of-frame is not treated as a quality defect on its own** — it's normal waist-up webcam framing (18% of all frames in the corpus) and excluding on it would be far too aggressive. Any future framing-quality signal should weight or gate on the 6 arm/shoulder landmarks, not hips.
- **`_vis` is not uniformly trustworthy as an out-of-frame proxy across landmarks** — wrist `_vis` is reasonably trustworthy (~5.5–8.7% false-confident when genuinely out of frame); hip and shoulder `_vis` are not (~50–52% and ~95–98% respectively). Don't build a single visibility-threshold gate that treats all landmarks the same way.
- **Occlusion-error detection from pose data alone is an open problem, not assumed solved or unsolved** — one naive geometric proxy was tested and failed (see "Occlusion-error detectability" below); don't build further automatic occlusion detectors without validating against real per-frame labels first, and don't assume manual annotation is the only path without trying at least one more feature.
- **The originally-planned Stage 2 (`defect_localization`, single warm-started span + cause per problematic clip) is effectively superseded by the `error_marking` task type** (built 2026-08-30: typed, multi-span, extensible error vocabulary) — see the note under "Implementation phasing" below. Don't build `append_defect_localization_tasks.py` as originally scoped without first deciding `error_marking` doesn't cover the need.
- **"Right hip"/"Left hip" are merged into one "Hips" body part; "Torso" is relabeled "Shoulders"** (2026-09-01, Viona's request) — see "Error-marking timeline redesign" for the migration mechanics. Don't reintroduce separate hip sides without her asking again.
- **The error-marking timeline's event listeners are delegated to the stable `#error-marking-timeline` container, never bound to individual segments/tracks/handles.** Those child elements get destroyed and recreated on nearly every interaction (a drag, a mark creation, a cause toggle); a per-element listener would either go stale (pointing at a detached node) or silently double-bind across re-renders. Keep this pattern for any further additions to that screen — see `attachTimelineHandlers()` in `app.js`.
- **A per-mark `note` field exists alongside the whole-clip note** — don't conflate the two or assume one supersedes the other; they answer different questions (what's specifically wrong with this one span, vs. anything else worth saying about the clip as a whole).

## Full architecture

See the complete design in [the plan artifact this session produced](#full-plan-text-below) — reproduced in full below so it survives independent of any local `~/.claude/plans/` file, which is not part of this repository and will not be available to a future session or a different machine.

### 1. Automatic quality-signal sweep — `motion_extraction/scripts/compute_automatic_quality_signals.py`

**Superseded in one respect**: this section originally planned to read participant studies' pre-canonical `legacy/` pose data via an in-memory adapter. That adapter was built, used for one full sweep, then removed in favor of actually re-extracting the whole corpus through the canonical pipeline on GPU — see the Status section's "What changed since the first Phase 1 pass". The signal-computation logic below (crop, lighting, windowed roughness, false-tracking) is otherwise still accurate; only the pose-data *source* changed, to `motion_extraction/scripts/extract_pose_landmarker_corpus.py`'s canonical output via `motion_extraction/corpus_videos.py`'s shared enumeration (52 reference + 675 study1 + 1,081 study2 = 1,808, not the 822/1,955 figures originally written here).

Per clip, compute:
- **Reuse as-is**: `normalized_acceleration_p95`, `finite_coordinate_fraction`, `usable_frame_fraction` — same as `_direct_quality_summary()` in `motion_extraction/scripts/run_preprocessing_experiment.py:122-154`, on B0 (unprocessed) clean pose.
- **New — frame-bounds crop signal**: read **raw** pose2d (pixel-space — clean pose is torso-normalized and cannot see frame position) for `LEFT_HIP`/`RIGHT_HIP`/`LEFT_SHOULDER`/`RIGHT_SHOULDER`, plus video width/height via `cv2.VideoCapture` (frame dimensions are not persisted anywhere else). Flag fraction of frames where these land near/off the frame edge.
- **New — lighting signal**: extend the existing `mean_luminance_0_255`/`luminance_contrast_sd` snippet in `append_targeted_preprocessing_tasks.py` to sample across a clip, not one frame.
- **New — windowed roughness**: rolling-window version of the p95 roughness calc (not just whole-clip), needed both to flag temporally-local problems and to drive Stage 2 warm-start localization.
- **New — coarse false-tracking heuristic**: frames where landmark velocity is kinematically implausible *and* visibility/confidence is low, co-occurring.

Output: one CSV row per clip under `temp/experiments/<name>/automatic_quality_signals.csv`, following the shape of the existing `pose_quality_by_file.csv`, plus `run_provenance.json`. Support `--max-files`; 1,955 clips will take a while — validate on a small slice first.

### 2. Stage 1 triage task generator — `annotation_tool/generate_quality_triage_tasks.py` (BUILT)

Built close to plan, one simplification: instead of a validated threshold-based "flagged" cutoff (none exists yet), each signal's candidates are the **top-N most extreme clips by that signal's raw ranking** -- the most informative test cases for judging whether the signal's ranking makes sense at all, and avoids inventing an unvalidated cutoff. A clip that ranks top-N on more than one signal is only shown once (fixed priority: crop, then roughness, then false-tracking; regression-tested). Reuses `_encode_frames`/`_draw_pose` from `generate_temporal_comparison_tasks.py` and `_pose_pixels`/`_write_review_frame` from `run_preprocessing_experiment.py` for rendering, and each signal's own `*_longest_run_start`/`windowed_roughness_worst_window_start` column (added to `compute_automatic_quality_signals.py` for exactly this) to center the frame/clip window on the actual flagged span, not just the clip midpoint.

- Emits `task_type: "quality_triage"` tasks into a fresh manifest, following the existing manifest-header shape (`schema_version`, `experiment_id`, `task_type`, `seed`, `input_provenance` with a signals-CSV sha256, `tasks`).
- Default batch: `--per-signal-count 15 --control-count 15` = 60 tasks. A real batch (`temp/experiments/20260828-quality-triage-batch-v1/`) is generated and ready to review.

### 3. Stage 2 follow-up generator — `annotation_tool/append_defect_localization_tasks.py` (not yet created)

## Implementation phasing (build/validate in this order)

1. **Signals only** (DONE) — `compute_automatic_quality_signals.py`, run over the full corpus.
2. **Triage end-to-end** (DONE) — `generate_quality_triage_tasks.py` + server + `#triage-screen`. A real batch was generated and reviewed (60 tasks, 34/60 by Viona so far, all 60 by Claude) — see Status above for the comparison results.
3. **Defect localization follow-up** (NOT STARTED, and likely superseded rather than built as originally scoped) — the plan was `append_defect_localization_tasks.py` + server + `#defect-screen` + warm start, auto-triggered from Stage 1's `problematic` verdicts, with one warm-started span + cause per clip. Real triage results now exist, and they changed the picture: the automatic signals don't correlate cleanly enough with "problematic" to make a good warm-start guess (crop doesn't predict it at all; false-tracking only localizes well if you already know which window to show), and a single-span-with-a-cause model is a poor fit for clips with several distinct errors of different types. **`error_marking` (built 2026-08-30 — see above) already covers this need more generally**: typed, multi-span marking with an extensible error-type vocabulary, manually driven rather than auto-triggered from a triage verdict. Before building `append_defect_localization_tasks.py`, decide whether `error_marking` plus a future "generate pending tasks for clips marked problematic without an error_marking follow-up yet" script (a much smaller addition, reusing `error_marking`'s existing schema) covers the need instead.
